# 08 — HHT Integration

## 1. How the device works

```
HHT Login
   ↓
Load required data          (shops, items, current stock for the shop)
   ↓
Scan products               ─┐
   ↓                         │  everything held in the device's
Enter / verify quantity      │  own local database
   ↓                         │
Complete stock scan         ─┘
   ↓
Final Share / Submit        ← the only moment anything is sent
   ↓
POST /api/hht/submissions
   ↓
Validation
   ↓
Audit header  +  Audit lines
   ↓
Web verification
```

### There is no continuous synchronisation

Scans are **not** sent one at a time, nor in batches during the count. The
device holds the entire count locally and sends it once, when the operator
presses Share / Submit. The server has no concept of a partial count.

This is deliberate: the shops count on unreliable connectivity, and a count is
only meaningful once it is finished.

---

## 2. Submission identity

A submission is identified by:

```
Shop ID  +  Device ID  +  Audit Number
```

**The audit number alone is not unique.** Several devices in one shop routinely
carry the same audit number, and each device advances its own sequence:

```
Shop PHM001, first round        Shop PHM001, later
  HHT-01 → Audit 1                HHT-01 → Audit 3
  HHT-02 → Audit 1                HHT-02 → Audit 3
  HHT-03 → Audit 1                HHT-03 → Audit 2
  HHT-04 → Audit 1                HHT-04 → Audit 2
```

Enforced by `audits.audit_identity_unique (shop_id, device_id, audit_number)`.
Nothing in the application treats the audit number as a key on its own, and every
screen that shows an audit number shows its shop and device beside it.

## 3. Endpoint

```
POST /api/hht/submissions
Authorization: Bearer <token>
Content-Type: application/json
```

### Request

```json
{
  "submission_uid": "SUB-PHM001-HHT-02-A3",
  "shop_code": "PHM001",
  "device_code": "HHT-02",
  "audit_number": 3,
  "audit_date": "2026-08-25",
  "hht_user": "Karthik Subramani",
  "app_version": "1.4.2",
  "items": [
    {
      "barcode": "8901234500011",
      "product_code": "MED-1001",
      "physical_quantity": 95,
      "batch": "B01001",
      "expiry": "2027-06-30",
      "uom": "STRIP",
      "shelf_location": "A-01"
    }
  ]
}
```

| Field | Required | Notes |
| --- | --- | --- |
| `submission_uid` | recommended | Generated by the device and kept until the server acknowledges. Drives idempotency. |
| `shop_code` or `shop_id` | yes | Either form is accepted, so the device need not carry server keys |
| `device_code` or `device_id` | yes | Must belong to the shop |
| `audit_number` | yes | Integer ≥ 1, the device's own sequence |
| `audit_date` | yes | Date the count was performed |
| `hht_user` | no | Who counted |
| `app_version` | no | Useful when diagnosing a device |
| `items[]` | yes | At least one entry |
| `items[].barcode` | one of | Barcode or product code must be present |
| `items[].product_code` | one of | |
| `items[].description` | no | Used when the product is not in the stock file |
| `items[].physical_quantity` | yes | Numeric, ≥ 0 |
| `items[].batch` | no | Improves stock matching |
| `items[].expiry` | no | |
| `items[].uom` | no | |
| `items[].shelf_location` | no | |

### Response — accepted (`201`)

```json
{
  "success": true,
  "message": "Submission accepted. Audit 3 for PHM001 / HHT-02 created with 42 item(s).",
  "data": {
    "submission_id": 88,
    "audit_id": 41,
    "audit_number": 3,
    "status": "accepted",
    "item_count": 42
  }
}
```

### Response — already received (`200`)

```json
{
  "success": true,
  "message": "This submission has already been received. The existing audit has been returned and no duplicate was created.",
  "data": {
    "submission_id": 88,
    "audit_id": 41,
    "audit_number": 3,
    "status": "duplicate_ignored",
    "item_count": 42
  }
}
```

### Response — refused

```json
{
  "success": false,
  "message": "The device in this submission is not registered against shop PHM001."
}
```

| Status | Cause | Device should |
| --- | --- | --- |
| 401 | Token missing or expired | Re-authenticate and retry |
| 422 | Unknown or inactive shop, unregistered or inactive device, empty items, negative quantity | Show the message; do not retry unchanged |
| 409 | A different count already exists for this shop, device and audit number | Show the message; use a new audit number |
| 500 / 502 | Server fault | Retry with the same `submission_uid` |

## 4. Duplicate submission handling

A dropped connection means the device cannot tell whether the server received the
count. The device should retry, and the server makes that safe.

```
Submission arrives
   │
   ├─ Is there an hht_submissions row with the same
   │  shop + device + audit_number + submission_uid?
   │        yes ──► return the existing audit, status = duplicate_ignored
   │
   ├─ Is there a row with the same shop + device + audit_number
   │  and the same payload hash (SHA-256 of the body)?
   │        yes ──► return the existing audit, status = duplicate_ignored
   │
   ├─ Is there already an audit for shop + device + audit_number
   │  with different content?
   │        yes ──► 409, refuse
   │
   └─ otherwise ──► create the audit in a transaction
```

Two layers, because a retry may lose its `submission_uid` (a reinstalled app, a
cleared cache) but the body will still be identical.

**Device guidance**

1. Generate `submission_uid` once, before the first attempt, and keep it.
2. Retry with the *same* uid — never a fresh one.
3. Treat `accepted` and `duplicate_ignored` alike: the count is safely stored.
4. Only clear the local count after one of those two responses.
5. Do not retry a `422` or `409` without changing something.

## 5. What the server does with a submission

```
transaction
  ├─ audits              header: shop, device, audit number, date, counted by, item count
  ├─ audit_lines         one row per counted product:
  │                        system_qty   ← snapshot from item_stocks
  │                        physical_qty ← from the device
  │                        variance_qty ← physical − system
  │                        is_unknown_item ← true when no stock row matched
  ├─ hht_submissions     the receipt, with the payload hash
  └─ devices.last_submission_at
commit
```

### Matching a counted item to stock

1. Match on `product_code` within the shop, otherwise on `barcode`.
2. If a `batch` was sent and a row matches that batch, prefer it.
3. Otherwise take the first matching row for that product in that shop.
4. If nothing matches, the line is stored with `system_qty = 0` and
   `is_unknown_item = true`. It appears on the audit as “Not in stock file”,
   cannot be adjusted, and is offered as a Stock Take candidate.

## 6. Authentication

The device uses the same token mechanism as the web application:

```
POST /api/auth/login   { "email": "...", "password": "...", "device_name": "HHT-02" }
        ↓
{ "data": { "token": "..." } }
        ↓
POST /api/hht/submissions   with  Authorization: Bearer <token>
```

Give each device its own account so the activity log attributes submissions
correctly, and deactivating a lost device is a single action.

---

## 7. Demonstration mechanism

Until the Android application is available, the **HHT Simulator**
(`/hht/simulator`) posts to the same endpoint with the same contract. It:

- holds the count locally and sends nothing until Share / Submit;
- lets an operator load a shop's shelf and alter physical quantities;
- can add a product that is not in the stock file;
- shows the duplicate response when the same submission id is sent twice.

It is a demonstration and testing aid. It does not change the contract, and the
real device needs no server change to take its place.

## 8. Open point

The payload above is our contract, authored for this build. If the client's
existing HHT application already emits a different shape, the mapping belongs in
`HhtSubmissionService::receive()` and nowhere else — the rest of the application
works from the audit and its lines. See `15-ASSUMPTIONS-DEPENDENCIES.md`.
